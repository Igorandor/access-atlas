# Campaign draft revisions

Verified September 27, 2026.

Settings and certification scope retained local draft fields when Reload campaign fetched a newer revision, but their saves used that newer revision automatically. A controlled reproduction edited the description at revision 1, then reloaded revision 2 with a title changed by another editor. Save details sent the old title and local description with revision 2, bypassing the intended conflict. Scope behaved similarly: a local prefix edit retained an old include-disabled value and could overwrite another editor's updated option. The actual parent/detail/certification callbacks reproduced both cases without bypassing disabled controls. Original evidence is retained outside the submission in `research/atlas-campaign-draft-revision-audit.mts` and `.json`; no native or existing campaign data was used.

Both forms now retain the revision and saved fields from which their draft originated. When a dirty draft encounters a newer campaign revision, its contents remain available and Save is disabled. A local notice explains that Use saved details or Use saved scope discards the draft and loads the current saved fields. This action is explicit and sends no request. Subsequent edits use that current revision. The parent forwards the expected revision supplied by these forms instead of replacing it with the latest selected revision; even a retained earlier callback still receives the server's ordinary conflict response rather than silently adopting newer data.

A clean form follows newer campaign data automatically. When an acknowledged save returns exactly the submitted fields, the form also advances its baseline, allowing the next edit without conflicting with its own completed save. An unrelated campaign update can still make a dirty draft stale; this deliberately preserves the existing whole-campaign revision boundary. Drafts are not merged automatically.

Four actual-component regressions cover both forms: draft preservation and blocked stale submission; explicit recovery retaining the other editor's fields; expected revision through the parent request; successful save followed by another edit; retained callbacks; and clean forms following unrelated later revisions. The component harness runs Campaigns, CampaignDetail, CertificationReview and the saved-evidence reader against an in-memory revision-checking transport. `npm run check` passes TypeScript, production builds and all **194 tests**. Existing decision forms, remediation workflows and cross-campaign selection behavior are outside this change.

Browser integration uses `research/atlas-campaign-draft-fixture.cjs` at port 3446 with the production client. The fixture contains one synthetic campaign. POST `{ "advance": true }` to `/_test/control` models another editor changing its title and include-disabled option; `{ "reset": true }` restores revision 1. GET `/_test/state` exposes the submitted revisions, accepted in-memory changes and zero native connections. The fixture serves only enumerated build assets and never connects to IRIS. Browser results are recorded separately by integration.

Production-client integration passed both Settings and Certification scope on desktop1280×900 and phone390×844 (375px content width). Each form retained its local draft after a concurrent revision and Reload, disabled stale Save and displayed its recovery instruction beside the form. Use saved details/scope explicitly loaded current fields; subsequent saves retained the other editor's title/include-disabled option and sent the expected current revision. Per viewport, exactly two accepted synthetic writes used revisions2 and4, with no stale request and no native connection. Evidence: atlas-draft-browser.json, desktop-state/mobile-state.json and four form/viewport screenshots under research outside the submission. These controlled checks do not establish native mutation behavior.
