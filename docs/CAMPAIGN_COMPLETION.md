# Campaign completion and readback

The closure audit reproduced two completion-policy gaps using the real campaign router and store in a new temporary directory: a current `investigating` decision allowed closure while every report readiness check passed; a submitted `uncertain` remediation allowed closure despite the report correctly requesting reconciliation. This was a completion-policy inconsistency, not an authorization bypass.

Closing now also requires completed finding investigations and readback of submitted changes. One shared predicate drives the route and report: `dispatching`, `uncertain`, `unverified` and `acknowledged` always require readback; `different` requires it until a nonblank reconciliation is recorded. An old note does not clear an uncertain status. The existing reconciliation endpoint reads the target and records either `verified` or `different` with the operator's note.

A recorded difference remains `different`, appears in the report and agenda, and is never counted as verified. Its agenda instruction describes the known mismatch and final finding decision instead of requiring repeated readbacks indefinitely. All finding and certification requirements still apply. Unsubmitted `reviewed` proposals and `failed` records alone do not prevent closure. These rules do not promise future native state or independently approve an accepted risk.

Archiving explicitly preserves unfinished work without marking it complete; it remains allowed with investigating findings or uncertainty. The existing active dispatch guard still prevents state changes during dispatch. Existing closed records are not migrated or reopened.

Verification uses actual Express routes and CampaignStore with synthetic GET responses, temporary documents and an execution stub that must never run. Four regression groups cover byte-for-byte unchanged refusal, investigating → final decision → close, all five readback-required statuses → recorded mismatch → close, nonblocking draft/failure/explained difference, and unfinished archive versus active dispatch. No native connection or write is involved.

The separate browser fixture `research/atlas-campaign-closure-fixture.cjs` (workspace research directory, port 3454) serves the current production build and one synthetic campaign. Navigate Access review → Campaigns → Investigation still open → Settings, enter a reason and try Close review. It returns 409 and leaves the document unchanged; `/_test/state` lists attempts with accepted flags. Report shows Investigations complete requiring attention. A current finding can be changed to Accepted with an explanation in the UI; closure then succeeds. `POST /_test/control` accepts `{ "reset": true }` or `{ "finishInvestigation": true }`; the latter requires a UI reload to read the new revision. The fixture is memory-only and has no native transport. Browser visibility/focus of a refused status change is a separate check, not established by route tests.

## Status-change feedback

A production-build browser check found that the global refusal message after Close review could sit above the visible Settings area (desktop alert bounds -533.55 to -444.55, with focus on the body; `research/atlas-closure-before-desktop.png`). Status changes now report the exact failure in a local alert beside their buttons. After each new failed attempt, that alert receives programmatic focus and scrolls into view once. The reason and settings draft are preserved. Reloads, unrelated rerenders and pending-state transitions do not focus an already announced failure again. A new attempt clears the previous message; success leaves no local refusal. Other operations retain their global error handling.

The parent mutation tracks whether the status request succeeded before refreshing the list. A subsequent list failure remains a global list error and cannot be mislabeled as a refused status change. Two actual parent/detail callback regression cases cover focused refusal, a repeated identical refusal, unchanged campaign/reason, reload without focus stealing, success and the successful-mutation/failed-list distinction. Browser confirmation of the final focus placement is recorded separately by the coordinating review.

Final production-build browser checks passed at 1280×900 and 390×844 (document widths 1265 and 375, with no horizontal page overflow). The local alert was fully visible and focused: desktop bounds 642–753, phone 513–667. A repeated refusal focused the new alert; Reload retained the reason without refocusing the old failure. The report identified the ongoing investigation on both layouts. Saving a terminal decision and closing then produced closed revision 3, removed the local refusal and satisfied the recorded readiness checks. The synthetic fixture recorded six refused attempts and two accepted memory-only changes, with zero native connections. Evidence is in workspace research/atlas-closure-browser-state.json, atlas-closure-browser-counters.json and atlas-closure-*.png. These UI checks complement, rather than replace, the actual route/store regressions. Full build and 218 Node tests passed.
