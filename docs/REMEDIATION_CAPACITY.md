# Remediation result capacity

Verified September 27, 2026.

The actual campaign router and store reproduced two failures with synthetic documents in a new temporary directory. With 999 history entries, dispatch saved entry 1000, the controlled execute stub returned success, and finalization failed with 409. A separate schema-valid document grew from 19,999,770 to 19,999,954 bytes when dispatch was recorded; its normal verified receipt then failed to save with 413. Reconciliation read the synthetic target successfully but hit the same caps, leaving each durable record at dispatching. No native request or existing campaign was used. Original scripts and results remain outside the submission in `research/atlas-remediation-quota-audit.mts` and `.json`.

CampaignStore now checks reserved capacity within the same exclusive change operation, after constructing the prospective document but before saving it. A dispatching remediation reserves two further history events: finalization and one reconciliation. Its byte reservation covers the existing schema maxima for message (2,000 characters), checked fields (100 names of 256 characters) and reconciliation (4,000 characters), along with event metadata, revision digits and timestamps. JSON control-character escaping provides a six-byte-per-character upper bound. The same exported bounds define the stored-record schema, whose limits are unchanged. This conservative budget can refuse dispatch before actual short receipts would fill the file; it guarantees room for bounded result metadata rather than relying on average response size.

Uncertain, unverified, different, acknowledged or failed results without a recorded reconciliation retain space for one reconciliation. Every subsequent store change preserves that reservation, including ordinary details changes and additional reviews. Reservations are counted for each unresolved record. They end after its first recorded reconciliation, including a different result: repeated checks beyond that point still obey normal history and byte limits. Verified results release their automatic reservation after finalization, so later unrelated changes may consume remaining room before an optional recheck. No history is trimmed, and neither the 1,000-event nor the 20,000,000-byte cap was increased.

While a dispatch is pending, the store accepts only a finalization or reconciliation naming that dispatch's review ID. This also closes the concurrent review route's ability to advance the campaign revision underneath an executing operation. If that second route prepared a memory ticket first, its existing failure handler cancels it. Live reconciliation is still blocked by the router's in-flight guard; matching reconciliation after an interrupted process remains possible.

Five regression groups use the real router and store with synthetic transport and verified fresh temporary directories. They cover refusal without execute or file changes near each cap, successful finalization and one matching/different reconciliation at the history boundary, protected recovery bytes against an ordinary edit, and concurrent review/wrong-completion rejection without a finalization conflict. `npm run check` passes TypeScript, production builds and all **212 tests**. Test-created directories are removed after each case. No UI behavior changed; existing 409/413 rendering displays the capacity explanation.

This preflight cannot guarantee writes against later filesystem failure, permission changes, disk exhaustion or process loss. A malformed out-of-contract receipt can still fail validation. Existing documents already at their limits are not migrated, truncated or silently repaired; an old full dispatching record may still require preservation/export and a new campaign. The guarantee applies to dispatches admitted under the new check, and only to the bounded metadata and one recovery observation described above. It does not prove that an observed state was caused by a particular administrative operation.
