# Lost apply response recovery

Verified September 27, 2026.

Both configuration proposals and campaign remediation previously retained an enabled Apply button after the gateway accepted an apply request but its response was lost. The configuration component could send the same review ID again; remediation also still described the proposal as unsubmitted. Server protections already prevented unrestricted reuse, but the interface neither explained uncertainty nor directed the operator to recorded evidence.

The components now consume a review ID locally when Apply starts. Repeated clicks, including a retained callback from the earlier render, cannot send it again. A missing response, unreadable successful response, or 5xx reply explains that the apply response did not confirm an outcome and shows the review ID. It explicitly distinguishes a failed response from a rejected change. This describes the historical response failure, so a subsequently loaded verified receipt is not contradicted by an ongoing claim that the outcome remains unknown. An explicit 4xx keeps the exact refusal. Draft fields and remediation reasons remain available; no new proposal or retry is created automatically.

Configuration recovery opens the existing read-only session receipts. The operator should inspect the matching review and fresh target state before preparing another proposal. Campaign recovery invokes the parent's existing read-only reload of the selected campaign; its current revision and durable remediation history update without remounting the same campaign's draft. The existing Read current state workflow can then reconcile the observation. These reads do not prove which operation caused a matching state and cannot reverse an already applied change.

Five regression groups exercise actual component callbacks with controlled responses: TypeError, unreadable 200, 503, explicit 400/403/409, repeated old callbacks, preparation failure, successful completion and read-only recovery with preserved drafts. The parent reload callback is controlled in these tests; production integration verifies its HTTP route separately. `npm run check` passes TypeScript, production builds and **189 tests**. No native request, new dependency or automatic write replay was needed.

Production-client browser verification used the isolated fixture on port 3439, which accepted a synthetic change and then truncated its established HTTP 200 response after sending headers. Configuration recovery retained the draft and exact review ID, disabled Apply and loaded a verified session receipt. Campaign recovery retained the reason and consumed-review guard while a read-only reload displayed the verified durable record. Desktop and mobile checks found no horizontal overflow (375-pixel mobile client/scroll widths). Final evidence is outside the submission in the integration workspace: `research/atlas-apply-established-response-browser.json`, with two apply requests and two accepted synthetic changes for two distinct review IDs. Screenshots are `research/atlas-apply-unknown-desktop.png`, `research/atlas-apply-recovery-mobile.png`, `research/atlas-campaign-recovery-desktop.png` and `research/atlas-campaign-recovery-mobile.png`.

The earlier `research/atlas-apply-campaign-browser.json` records a fixture disconnect before response headers and two requests for one accepted change. It is retained as a historical transport observation, not evidence of an application retry. The final fixture establishes its response before disconnecting. These browser checks did not connect to IRIS or apply a native change.
